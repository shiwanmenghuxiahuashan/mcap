# `writer.cpp` 逐段精读

> 本文是 [writer.cpp](./writer.cpp) 的学习笔记，不是上游代码或官方文档。
> 目标：读懂这个示例如何把 Protobuf 消息写进 MCAP 文件，并理解 MCAP 的
> Schema → Channel → Message 数据模型。

这个程序做的事：生成 **100 帧点云**，每帧 1000 个点，球半径逐帧变大，写成一个
MCAP 文件；用 Foxglove 打开可以看到一个不断膨胀的球。

## 1. 文件头：编译期设置（L1–18）

```cpp
#define MCAP_IMPLEMENTATION
#include "mcap/writer.hpp"
```

这两行决定了这个库怎么被使用：

- **`MCAP_IMPLEMENTATION` 必须定义在 include 之前**。mcap 的 C++ 实现是
  header-only 的：`writer.hpp` 末尾有
  `#ifdef MCAP_IMPLEMENTATION #include "writer.inl" #endif`。定义了这个宏，
  当前编译单元才会把实现代码编进去。
- **整个程序只允许一个 `.cpp` 定义这个宏**，否则链接时重复定义。
- 这里 include 的是 `writer.hpp` 而不是聚合头 `mcap.hpp`——写文件只需要 writer。
- `#include "foxglove/PointCloud.pb.h"` 这个头**不在仓库里**，是 CMake 构建时用
  `protoc` 从 `proto/foxglove/*.proto` 生成到 `autogenerated/` 目录的
  （见 [`CMakeLists.txt`](./CMakeLists.txt) 的 `add_custom_command`）。
  所以 protobuf 示例依赖 `protobuf` 库；对照之下，`jsonschema` 示例只需头文件库。
- L15–18 的宏定义了：每帧间隔 100ms、每帧 1000 点、每点 3 个 float。

## 2. PointGenerator：造数据（L20–40）

这部分和 MCAP 无关，是纯数学：在球面上均匀采样随机点。

```cpp
theta = 2π * u1;              // 经度均匀
phi   = acos(1 - 2*u2);       // 纬度按 acos 变换，保证球面均匀
x = sin(phi) * cos(theta) * scale;
y = sin(phi) * sin(theta) * scale;
z = cos(phi) * scale;
```

- `std::mt19937` + 固定种子 `0` → **每次运行输出完全相同**，方便复现和对比。
- L137 的 `auto [x, y, z] = ...` 是 C++17 结构化绑定。
- `M_PI` 在 MSVC 下需要 `_USE_MATH_DEFINES`，`CMakeLists.txt` 里正是这样加的，
  否则编译不过。

MCAP 完全不关心这些业务数据是怎么生成的。

## 3. 打开文件（L42–58）

```cpp
mcap::McapWriter writer;
auto options = mcap::McapWriterOptions("");
const auto res = writer.open(outputFilename, options);
if (!res.ok()) {
  std::cerr << "Failed to open " << outputFilename << ": " << res.message << "\n";
  return 1;
}
```

- `McapWriterOptions("")` 的参数是 **profile**（录制配置标识，例如 ROS1/ROS2
  有约定值），空字符串表示不声明。
- 默认配置值得知道（`cpp/mcap/include/mcap/writer.hpp:67-78`）：
  - `chunkSize = 1 MiB`：未压缩数据攒够约 1 MiB 就切一个 chunk；
  - `compression = Zstd`：chunk 默认用 zstd 压缩；
  - 默认写 Message Index、Chunk Index 和 Summary。
  也就是说，**分块和压缩默认就开**，不需要手动做。
- `open()` 返回 `Status`，用 `ok()` / `message` 检查错误——这是该库统一的错误
  处理风格，不是异常。

## 4. Schema 和 Channel：MCAP 的核心模型（L60–81）

先看源码注释（L63–65），这是全文件最重要的一段：

> messages 对 channels 是多对一；channels 对 schemas 是多对一。

```
Message ──channelId──> Channel ──schemaId──> Schema
```

```cpp
mcap::Schema schema(
  "foxglove.PointCloud", "protobuf",
  foxglove::BuildFileDescriptorSet(foxglove::PointCloud::descriptor()).SerializeAsString());
writer.addSchema(schema);

mcap::Channel channel("pointcloud", "protobuf", schema.id);
writer.addChannel(channel);
channelId = channel.id;
```

几个名字要分清：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `Schema.name` | `"foxglove.PointCloud"` | protobuf 消息的**全限定名**，读取时靠它找类型 |
| `Schema.encoding` | `"protobuf"` | schema 本身用什么编码存储 |
| `Channel.messageEncoding` | `"protobuf"` | 每条 message 的 payload 用什么编码 |
| `Channel.topic` | `"pointcloud"` | 话题名，给人看的 |

### 为什么 schema 是 FileDescriptorSet？

protobuf 的 schema 在 MCAP 里存的是 **`FileDescriptorSet`**，也就是 protobuf
自带的描述符二进制格式，等价于：

```bash
protoc --include_imports --descriptor_set_out=filename your_type.proto
```

`PointCloud.proto` import 了 `google/protobuf/timestamp.proto`、`Pose`、
`PackedElementField`，而 `Pose` 又 import 了 `Vector3` 和 `Quaternion`。
只存 PointCloud 自己的描述，读取方会遇到未知类型。

所以 [`BuildFileDescriptorSet.cpp`](./BuildFileDescriptorSet.cpp:10) 做的是
**依赖图 BFS**：把目标文件及所有传递依赖都放进同一个 `FileDescriptorSet`。
这样动态读取器（不需要生成代码）才能完整还原类型。

### addSchema / addChannel 何时落盘？

`addSchema` 只是登记到内存并分配 ID（从 1 开始），`addChannel` 同理；
**真正的 Schema/Channel 记录是在该 channel 的第一条消息写入时才落盘**
（`cpp/mcap/include/mcap/writer.inl:566-580`）。

## 5. 构造一条消息（L83–117）

这里操作的是 protoc 生成的 `foxglove::PointCloud` 类，字段对应
[`PointCloud.proto`](./proto/foxglove/PointCloud.proto)：

```proto
message PointCloud {
  google.protobuf.Timestamp timestamp = 1;
  string frame_id = 2;
  foxglove.Pose pose = 3;
  fixed32 point_stride = 4;
  repeated foxglove.PackedElementField fields = 5;
  bytes data = 6;
}
```

代码依次做：

1. **`point_stride = 12`**：每个点占 `3 * sizeof(float)` 字节。
2. **用 `fields` 描述 `data` 的内存布局**：三个 `PackedElementField`，名字
   `x` / `y` / `z`，offset 分别为 0 / 4 / 8，类型 `FLOAT32`。这就是"自描述"：
   任何读取方不用知道 C++ 结构体，照着布局表就能把 `data` 解释成点云。
3. **`mutable_data()->append(12000, '\0')`**：protobuf 的 `bytes` 在 C++ 里映射
   为 `std::string`。先扩到 `1000 × 3 × 4 = 12000` 字节的零填充缓冲区，后面直接
   `memcpy`。**不要 1000 次 `add_points()`**——批量二进制比逐字段编码快得多。
4. **设置 `pose`**：位置 (0, 0, 0)，四元数 (0, 0, 0, 1) 表示单位旋转；
   `frame_id = "pointcloud"` 是坐标系名字。

## 6. 主循环：写 100 帧（L119–162）

时间与缩放：

```cpp
startTime  = system_clock::now() 的纳秒数
cloudTime  = startTime + frameIndex * 100ms
cloudScale = 1 + frameIndex / 50        // 1.0 → 2.98，球越来越大
```

每帧做四件事：

1. **更新 `pcl.timestamp`**：protobuf 的 Timestamp 拆成 `seconds` + `nanos`。
2. **填 1000 个点**：`memcpy` 把 3 个 float 写到 `data` 的
   `offset` / `offset+4` / `offset+8`。这里假设主机是小端——`PackedElementField`
   注释写明整数按 little-endian 存储，主流平台都是 LE。
3. **`pcl.SerializeAsString()`**：把整个消息（含 12KB 的 `data`）编码成
   protobuf 二进制。
4. **填 `mcap::Message` 并写入**——这是 MCAP 视角下的一条消息，字段很少：

```cpp
mcap::Message msg;
msg.channelId   = channelId;                  // 指向注册的 channel
msg.sequence    = frameIndex;                 // 同一 channel 内递增
msg.publishTime = cloudTime;                  // 纳秒时间戳
msg.logTime     = cloudTime;                  // 录制时间；拿不到发布时刻时两者相同
msg.data        = reinterpret_cast<const std::byte*>(serialized.data());
msg.dataSize    = serialized.size();
const auto res  = writer.write(msg);
```

**易错点**：`Message.data` 是裸指针，MCAP 不拷贝它，指针只在下一次调用前有效。
这里 `serialized` 是局部变量，在 `write()` 返回前一直活着，所以安全；
如果写成 `msg.data = tmp.c_str()` 且 `tmp` 先析构，就是悬垂指针。

写入失败时：

```cpp
writer.terminate();                 // 放弃收尾，不写索引/footer
std::ignore = std::remove(outputFilename);  // 删掉半成品
```

`terminate()` 和 `close()` 是两条路：前者放弃，后者正常收尾。

## 7. 收尾：close 做了什么（L163–166）

```cpp
writer.close();
```

这一行做的事（`cpp/mcap/include/mcap/writer.inl:397`）：

1. 把最后一个 chunk 刷盘（压缩 + 写 Chunk 记录）；
2. 写 **Data End** 记录；
3. 写 **Summary**：重复的 Schema/Channel、Chunk Index、Message Index、
   Statistics（消息数、起止时间等）；
4. 写 **Footer** 和结尾 magic。

没有这一步，文件可能还能顺序扫描，但**没有索引**，随机访问和完整校验都无从
谈起。"忘了 close"是写 MCAP 最常见的问题之一。

## 整体数据流

```
.proto ──protoc──> PointCloud.pb.h
                        │
PointGenerator ──> PointCloud 对象 ──SerializeAsString──> bytes
                        │                                   │
               FileDescriptorSet                    mcap::Message
                        │                                   │
                        └──────── Schema + Channel ──── writer.write
                                                            │
                                                   chunk(zstd) + index
                                                            │
                                                         close()
                                                            │
                                                      output.mcap
```

## 关键 API 速查

| API | 作用 |
| --- | --- |
| `McapWriter::open(filename, options)` | 打开文件，返回 `Status` |
| `McapWriter::addSchema(Schema&)` | 登记 schema，分配 `id`（从 1 开始） |
| `McapWriter::addChannel(Channel&)` | 登记 channel，分配 `id`；首次写消息时落盘 |
| `McapWriter::write(const Message&)` | 写一条消息（payload 为非拥有指针） |
| `McapWriter::close()` | 刷 chunk、写 DataEnd/Summary/Footer |
| `McapWriter::terminate()` | 放弃收尾，重置 writer |

## 三个易错点

1. **`#define MCAP_IMPLEMENTATION` 只能出现在一个编译单元**，且必须在 include 之前。
2. **`Message.data` 不拷贝**：payload 必须活到 `write()` 返回。
3. **必须 `close()`**：否则没有索引和 footer；异常路径用 `terminate()` 并清理文件。
